# 09 手机渲染性能(场景美术这一侧)

来源标记:〔读〕〔测〕〔推〕同 01。主要来源:Unity 6000.3 手册(SRP Batcher、合批、GPU Resident Drawer、贴图格式、mipmap、遮挡剔除、URP 性能配置、自写 shader 优化各页)、Unity 电子书《Optimize your game performance for mobile, XR, and the web (Unity 6 edition)》(2024,读了图形和资源部分)、Arm GPU Best Practices Developer Guide 3.4 版(2025-01)、Android 开发者站转载的 Arm 几何、贴图、材质、顶点数据四篇(没有日期,例子偏旧)、Imagination PowerVR 文档站的性能建议各页、Qualcomm 的 Adreno 最佳实践。灯和阴影的上限、SSAO 的成本在 04 和 03,这页不重复。手机性能建议老得快,数字都标了出处,用之前看年代。

## 一、合批

- SRP Batcher 不减 draw call 数量,减的是 draw call 之间的渲染状态切换:材质数据常驻 GPU,同一个 shader 变体的材质连着画时不重新设置。省的是 CPU 时间。一个批能多长取决于 shader 变体:同一个 shader 配多少个不同材质都不断批,变体不同就断。〔读〕
- 兼容条件:物体是网格(不是粒子);不用 MaterialPropertyBlock;shader 的所有材质属性在名为 `UnityPerMaterial` 的常量块里,引擎内置的逐物体属性在 `UnityPerDraw` 里。只要有一个材质属性在块外,整个 shader 不兼容。shader 的 Inspector 上能看兼容状态。〔读〕
- 会打断的:MaterialPropertyBlock;不同的 shader 变体(关键字不同);脚本里访问 `Renderer.material`(会复制一份材质,用 `sharedMaterial`)。同一网格要不同颜色用 Material Variant 或顶点色。〔读;顶点色推〕
- 怎么看:Frame Debugger 里展开 `RenderLoopNewBatcher.Draw`,每个 SRP Batch 显示装了多少 draw call、挂了哪些关键字、没和上一个合上的原因。很多批里都只有几个 draw call,说明变体太多。〔读〕
- 几种方法的关系(6000.3 手册):URP 推荐开 SRP Batcher;材质上的 GPU Instancing 勾选关掉(免得多出变体);动态合批不再推荐。GPU Instancing 和 SRP Batcher 互斥。大量完全相同的网格加完全相同的材质时,instancing 可能更高效,要量。〔读〕
- GPU Resident Drawer(Unity 6):要求 Forward+ 路径、shader 支持 DOTS Instancing、构建里保留全部 BatchRendererGroup 变体;手册说开了它就不该再用静态合批。我们是 Forward 路径,不换路径用不了;GPU 遮挡剔除依赖它,同样用不了。〔读;结论推〕

## 二、静态合批还是在 Blender 里合

- 静态合批把网格按世界坐标合进大的顶点缓冲。代价是内存:同一个模型摆 N 次,顶点数据存 N 份,手册的例子是密林里把树都标成静态对内存影响很大。它保留逐个网格的剔除;但中间有网格被剔掉时,一批会被拆开。〔读;N 份是按原文推〕
- 手动合并(在建模软件里合,或 `Mesh.CombineMeshes`):适合靠得近、不相对移动的件;合完一次 draw call;代价是不能单独剔除,只要有一部分在屏幕上整个都画。〔读〕
- Arm 的取舍:批不要大到让视锥剔除和从前到后排序失效。draw call 的大致指导是 OpenGL ES 每帧少于 500、Vulkan 少于 1000(2025 年,针对当前 Arm GPU)。〔读〕
- 用到街区(推断):一栋楼自身的墙、窗框、线脚、屋顶件总是一起出现,按「一栋楼」或「一个地块」合成一个或几个网格;不要把整个街区合成一个(俯视镜头一屏只看到街区的一部分)。合并的前提是同材质,颜色走顶点色或共用一张小图集正好满足。要单独开关、破坏、被脚本改的件不合。合完单网格不超过 65,535 顶点(16 位索引)。
- 静态合批怎样处理光照图 UV,没读到。

## 三、贴图

- ASTC 各块大小的位数和一张 1024 图的大小(Unity 手册):

| 块 | 位每像素 | 1024×1024 |
|---|---|---|
| 4×4 | 8 | 1.0 MB |
| 5×5 | 5.12 | 0.64 MB |
| 6×6 | 3.56 | 0.45 MB |
| 8×8 | 2 | 0.25 MB |
| 10×10 | 1.28 | 0.16 MB |
| 12×12 | 0.89 | 0.11 MB |

- 固有色、法线、遮罩各用哪档块大小,没有读到任何官方推荐表,各家只说块越小质量越高。读到的相关事实:ASTC 存法线只存 X、Y 两个分量;没有 1 位镂空 alpha,有 alpha 就是完整一个分量;位数越低,GPU 读贴图占的内存带宽越少,带宽常常是帧率瓶颈。〔读〕
- 通道打包:只用单通道的几张图(遮蔽、粗糙度、金属度)打进一张图的三个通道,细节最多的放绿色通道,打包图设成线性。非颜色贴图可以比固有色低一档分辨率。〔读〕
- mipmap:内存多三分之一;离相机距离会变的贴图要开,它同时提升质量和性能(缓存命中、带宽);屏幕上大小固定的不用开。三线性的采样成本是双线性的两倍。〔读〕
- 贴图大小按用途定:物体在允许的最近距离上大约一个屏幕像素对一个贴图像素;具体的「手机最大用多少」没读到硬数字。关掉 Read/Write,否则内存翻倍。〔读〕
- 图集:在 SRP Batcher 下不同贴图的材质只要是同一 shader 变体就不断批,所以图集对我们的主要好处是能把件合进同一个网格和同一个材质,以及减少贴图数。〔推〕
- Mipmap Streaming 按相机只加载需要的 mip 层级;自写 shader 的贴图属性要带对应的 `_ST`,否则可能算不对层级。怎么开和预算怎么设没读。〔读〕

## 四、透明、镂空和重复绘制

- alpha 混合:Mali 上混合本身不贵,贵在它关掉了去除重复绘制的优化(提前深度测试、FPK),所以贵在层数。不透明物体一定要关混合。〔读 Arm〕
- alpha test(clip / discard)为什么在手机上贵:不透明的图元在光栅化早期就能写深度;带 discard 的要等片元 shader 跑完才知道可不可见,后面的图元得等它。PowerVR 明说这是很多分块渲染平台的通病,建议优先用混合而不是 discard;Mali 上 discard 强制晚做深度测试;Adreno 上 discard 关掉提前深度拒绝。Unity 也建议自写 shader 避免 discard 和 clip,确实要用就做成材质开关,让不需要的物体不走它。〔读〕
- 混合和镂空谁更快,三家说法不完全一致(PowerVR 偏向混合,Arm 两个都要求少用,Android 页说要实测),落到具体机型要量。〔读〕
- 绘制顺序:不透明从前到后,然后镂空,最后混合的从后到前。PowerVR 的隐藏面消除不依赖不透明物体的顺序;Mali 新硬件(G725 起)也不依赖,老的依赖。〔读〕
- 深度预通道在手机上不要:Unity 文档写手机上 Depth Priming 设 Disabled(分块渲染的手机上运行时不支持,开 MSAA 时也不支持);Arm 说预通道让 draw call 和顶点处理翻倍,通常超过省下的重复绘制;PowerVR 说它已经由硬件做了。〔读〕任何会带回深度法线预通道的东西(SSAO 用 Depth Normals 源、DBuffer 贴花、贴花的 Rendering Layers)都要算上这笔。〔推〕

## 五、几何

- 一帧多少三角形,Unity 的手册和电子书都没给数。唯一的例子是 Arm 的一个老 demo:每帧约 21 万三角形稳定在约 30 帧,最大的物体约 3000 三角形,士兵每个约 360(年代和设备不明,只当数量级)。〔读〕
- 微三角形:三角形太小时 GPU 做了全部处理却对画面没贡献。三家的门槛不一样:Adreno 是每个三角形至少着色 4 个像素,Mali 是至少 10 到 20 个片元,PowerVR 是不低于 32 像素。细长三角形(一维小于 10 像素却拉得很长)比别的更贵,尽量接近等边;三角扇的中心点要避免。〔读〕
- LOD:相机和物体距离变化小的游戏不值得做。俯视固定高度的镜头应该直接按这个镜头距离定面数,把永远看不到的面(楼底、背面)删掉。Unity 6 的 Mesh LOD 在静态合批下永远用最高一级。〔读;俯视那句推〕
- 顶点属性:常见浪费是所有属性都用 32 位浮点。法线、切线、顶点色用 16 位够;位置单独一个流;常量不要存成顶点属性。导入设置里用不到法线切线就关。硬边和 UV 接缝会让顶点翻倍。〔读〕
- 顶点色比贴图省在哪:没有资料直接对比。由读到的句子拼出来:省掉贴图采样(每多一张图多一次采样,占内存带宽);不同配色的件可以共用一个材质,利于合并和合批。代价是每个顶点多一个属性,颜色边界要靠拆顶点。〔推〕

## 六、shader

- `half` 是 16 位,手机上省带宽、省电、更快;精度不够会出色带或抖动,世界坐标这类用 `float`。`half` 在桌面平台上等于 `float`,所以精度问题必须在手机上验。Mali 说高精度最多用两倍资源、速度减半;Adreno 说片元里用 16 位能效和性能可以到两倍。〔读〕
- 片元里要少的:discard 和 clip(第四节);动态分支(GPU 按最复杂的分支分配,还可能两边都执行);开方、对数、指数、三角函数、除法;贴图采样数(手机上越少越好);写深度。`normalize` 的代价没有资料专门讲。〔读〕
- 把计算挪到顶点:片元数通常比顶点数多。但顶点传给片元的数据太多时反而慢;大平面顶点稀,逐顶点光照会有插值误差。〔读;后一句推〕
- 变体:少用关键字、多用材质属性;运行时不切的开关用 `shader_feature`,并且不要拿它在运行时切(打包时可能被裁掉);裁变体能减构建时间、包体、加载时间和内存。〔读〕

## 七、分辨率、抗锯齿、帧率

- Render Scale 设到 1 以下只缩游戏画面,界面仍按原生分辨率画;放大滤波用双线性。新手机分辨率很高,不要用原生分辨率。〔读〕
- MSAA 在分块 GPU 上相对便宜的条件:多出来的采样留在片上内存里,写回时才解析。Mali 说 4 倍不贵;PowerVR 说 2 倍几乎免费、4 倍有明显影响;Adreno 建议优先用 MSAA,小像素的屏可以考虑不做抗锯齿。Unity 的说法是分块 GPU 上、没用后处理抗锯齿和自定义 feature 时,MSAA 比别的抗锯齿便宜;但开了 Opaque Texture 之类迫使中间目标写回内存的东西就不便宜了。〔读;最后一句推〕
- HDR:不需要就关,需要就 32 位;64 位带宽翻倍。〔读〕
- 其它 URP 开关:不需要时关 Depth Texture 和 Opaque Texture;相机数量越少越好(低端机上每个相机最多可能占 1 ms CPU)。〔读〕
- 帧预算:手机上只用目标帧时间的约 65%,留给散热,30 帧约 22 ms、60 帧约 11 ms;可以考虑 30 帧作为折中。真机测的时候设备发热数据会变差,分短段测,两次之间冷 10 到 15 分钟。〔读电子书 2024〕

## 八、剔除

- 视锥剔除是自动的;在 CPU 侧整件剔掉永远比交给 GPU 逐三角形剔高效。〔读〕
- Unity 内置的遮挡剔除每帧有 CPU 查询成本和内存成本,最适合房间走廊式的结构,最可能有收益的情况是因重复绘制而 GPU 受限。俯视镜头里楼顶和街面基本都直接可见,楼之间互相遮挡的面积小,按手册的适用条件大概率不值。〔读;结论推〕
- 俯视镜头下更有效的:合并的粒度别太大、不透明从前到后、把相机远裁剪面收紧到刚盖住地面、小物件单独一层用 `Camera.layerCullDistances` 设更短的剔除距离。〔后一项读;其余推〕

## 九、怎么量,预算怎么定

- 先判断是 CPU 受限还是 GPU 受限:Unity Profiler 里频繁看到 `Gfx.WaitForPresent` 是主线程在等 GPU,看到 `Gfx.WaitForCommands` 是渲染线程在等主线程。〔读〕
- Frame Debugger 看批和断批原因;URP 的 Rendering Debugger 有 Overdraw 视图;Scene 视图也有 Overdraw 模式。〔读〕
- 厂商工具:Arm Performance Studio 的 Streamline 能看每像素片元数(去掉透明物体后大于 1 说明有不透明的重复绘制)、被晚深度测试杀掉的片元数、图元剔除率、带宽;Mali Offline Compiler 离线看 shader 的指令周期;Android GPU Inspector 支持三家 GPU 的计数器。〔读〕
- 在目标真机上测,最低配和最高配都测,改之前改之后都测。编辑器里的帧率不等于真机。〔读〕
- 能当预算锚点的数:帧时间按 65% 取;draw call 少于 500(GLES)或 1000(Vulkan);三角形不小于 4 到 32 像素(看 GPU);不透明的每像素片元数接近 1;单网格 65,535 顶点以内;贴图内存按上面的位数表直接算,带 mip 再加三分之一。〔读〕
- 定一个街区的预算(推断):在最低配真机上跑最密的一屏,先分清 CPU 还是 GPU 受限;CPU 侧记可见 renderer 数、批数、材质和变体数;GPU 侧记渲染分辨率、透明层数、每材质采样数、最小三角形的屏幕面积;内存侧记贴图和合并网格。超了先合网格减材质,再减面,再降分辨率。
