# Lead 调度规则(总控带子会话)

这份规则来自 2026-10-16 荒漠样板两天的复盘:效率损失大部分出在 lead 身上,执行方本身不慢。每条规则对着一次真实的浪费。看图验收的方法另见 reference-replicate。

## 1 口径写成带版本的 spec 文件,聊天只发指针

子会话跑长回合时,lead 的消息排队,按到达顺序被逐条执行,lead 也不知道哪条已被读到。10-16 砖块套件先读到旧的"保厚 0.14-0.16",后面"加厚"还在排队,白做一轮。

- 每条线一个 spec 文件,放共享笔记目录:`spec_<线名>.md`,模板见 `templates/spec.md`。文件头写版本号和"vN 覆盖 vN-1"。
- 聊天消息只说"spec_X 升到 vN,读文件",不在消息里另写一套口径。
- 执行方每轮开工先读 spec 文件,交付回报第一行写"按 spec_X vN"。版本对不上,lead 直接退回。

## 2 spec 里每个数字都有出处,改数要有新证据

lead 自己来回改口径(砖厚先减后加、碎块先圆后尖、尺寸拍脑袋)比执行方犯错更费轮次。

- spec 每一条要么指向观察表某一行(参考文件、坐标、实测值),要么指向用户拍板(Sheet 节号或原话)。
- 要改一个数,先有新证据:重新量过、用户新拍板、在景验证发现矛盾。改动写进 spec 的变更记录,说明依据。没有出处的改动不许发。
- 用户的话按原话记,不升级:"大约可以接受"不写成"通过","看着不错"只对他指的那一件。

### 2b spec 发出前的检查(10-16 草皮 r3、草甸 v1 教训)

- 每一条要求必须填"对应参考的哪一段"(文件 + 坐标)。填不出的不许发。
- **禁止"加/补某个形状"的要求,除非能指出参考里对应的那一段。** 10-16 v2"沿边按分布加叶瓣""零星叶探出崖沿"让执行方回到参数生成,做出圆泡和水滴,比上一版还差。
- 每条视觉要求都要加一列"机制":写清在本项目着色器下这个效果靠什么出来,是光照、顶点色、ramp、贴花,还是烘焙 mask。10-16 丛林七份 spec 过 Fable 关口,崖壁、草地、阶梯山地、树木四份都栽在同一类问题上:spec 只写了"要渐变 / 要三档明暗 / 要软影",可 LabLit 平涂二分光本身做不出这些效果,第一轮注定是一刀切的硬边。
- 颜色要写明是"屏幕色"还是"材质色"。屏幕色要闭环标定:在本项目的光下截图取色,反推材质色。10-16 舞台 r1 把屏幕色 #9EB75E 直接填进了材质,太阳一照成了亮黄。
- 观察者"推断"出来的项(没有直接样本)不进要求,写进待核。10-16 草甸 v1"遮到膝盖到大腿"就是两名观察者推断、Fable 用角色放大图否掉的。
- 主体件、地面、整屏的 spec 发给执行方前,必须过一次 Fable 关口:只给裁好的同比例参考图 + 合并观察表 + spec,问"照这个做第一轮会在哪里不像",≤5 条。10-16 草甸一次拦下 3 处总控和双观察者都漏掉的错,约 9 万 token。

### 2c 第一轮只交摆位稿

新物件第一轮不做形状和材质细节,只交"摆位稿":纯色占位块在本项目相机下摆好位置、朝向、大小、贴着哪条边界,和参考同比例叠图对照。lead 确认后才进形状和材质。10-16 草皮两版都卡在叶瓣大小上,真正影响"像不像"的是整块转了 90°、孤立摆在砂地中间,本该第一步定。摆位要求必须给出参考里对应那一块的两端、宽窄变化和它贴着/压着什么,不能只写方向(10-16 草皮 v3 只写"长轴沿崖沿",被做成横贯全屏的绿带)。摆位要求里的尺寸先在本项目相机画面里量一遍容量再写(10-16 草甸写了"长 5.5-7.4H",V5 竖屏全宽只有 5.37H,执行方两次停下来问);小取舍授权执行方自定,只给不可违反的几条底线。摆位稿只做纯色占位,完整生成器等摆位确认后再写(10-16 草甸先写完整个生成器才交摆位稿)。体量较大的新资产(草甸、崖壁)在摆位稿之后再做一小块测试块,过了才铺开。
验收多屏摆位稿时,先拿 scope 清单逐项点名:每一项在哪一屏、单看灰盒能不能认出是它。几项被合成一个东西的,要拆开。10-16 丛林 P1 把"地面上的台地"和"世界边缘"做成了一列下跌的台阶,总控只挑了规整感,是勾哥指出两样都没有。

## 3 验收一次给全,执行方回合中不追加零碎

10-16 砖地缝色、缝宽、裂纹、碎块下沉、接触暗分成五条消息,变成四轮交付。

- 每次验收按 reference-replicate 第 4 节,从头到尾全部量完,一张清单一次发出(同时更新 spec 版本)。
- 修改单除了"改什么",还要写"必须保留"哪几项已认可的特征。10-16 崖壁按勾哥"草皮翘起来了,要贴合崖壁"去修,执行方把草皮和台地平面求交,外翘没了,勾哥 #40 要的垂盖叶瓣也一起砍掉,多开一轮。只写文字不够:10-16 22:3x 崖壁 r3d 修改单写了"必须保留垂盖贴崖",交件里垂盖还是没了。保留项要变成交件的一格验收图(和修前同机位并排,标出那几项),执行方交件前自己对一遍。
- 执行方回合进行中,不追加零碎消息。真有急事:先 stop_session 它的回合,再发合并后的完整清单。
- 子会话派单写死"每交一轮就结束回合",别开超长回合。

## 3b 什么时候算 OK、什么时候停(10-16 草皮越改越坏后定)

"找不出三处差异才算过"没有终点,差异永远找得到;拿放大图和够不着的指标去追,会一轮比一轮加工得多、越改越坏(草皮 r2→r3→v3:B 块零加工最好,A 块每轮加工都在退步)。所以:

1. **开工前定"完成线"**:每类物件只列 3-5 条在实机尺度(V5 全屏、手机实际大小)看得出的关键项,写进 spec。验收只看这几条,不在放大图上找新问题。
2. **差异分两类**:实机全屏看得出的才开新一轮;放大才看得出的(像素阶梯、细尺度起伏、几个 px 的色差)只记录,不开轮。
3. **够不着的指标直接放弃**:受参考分辨率限制达不到的数(如细尺度 0.46),不追,写进"已知限制"。
4. **每轮必须赢过当前最好版**:在完成线几项上和最好版 A/B 并排(实机尺度),没赢就回退并停下,不再开下一轮,除非有新的参考信息。
5. **轮次上限**:同一物件最多 3 轮。到上限冻结当前最好版,把最好版和"建议冻结"给用户看,由用户决定是否再开。
6. **用户说可以就冻结**:"大约可以接受""这块就很好"都是冻结信号,当轮冻结,不再为它开轮;剩下的差异记进待办,等整屏收差距时统一处理。

## 3c 第二轮起让用户判,并从他的判断里学标准(勾哥 10-16 定)

- 每个物件做完第一、二轮后,从第二轮起每轮把"当前最好版 vs 本轮"实机全屏并排,用弹窗让用户判:冻结 / 再改一轮(写清改什么)/ 方向不对。lead 先把自己的判断写下来,再看用户选。
- 维护一份"用户判断标准库"(共享笔记,如 15_勾哥判断标准库.md):每条记时间、看的是什么、原话、lead 当时的判断、差在哪、推出的标准。原话照记,不升级不降级。
- 每次验收前先读标准库;lead 和用户判断不一致时以用户为准,把推出的标准写回标准库,能泛化的再写进 reference-replicate 或本 skill。
- 目标是 lead 的判断逐步和用户对齐,用户需要介入的次数逐轮减少;每周期看一次"lead 判断与用户一致的比例"。

## 3d 认可即入做法库,新物件先查做法库(勾哥 10-16 定)

- 用户认可/冻结一套做法的当轮,lead 写一张做法卡进项目的做法库(ER:vault `013 美术/复刻做法库/`):认可原话 / 一句话做法 / 步骤与工具(脚本、命令、参数)/ 换环境时要重新取的 / 不要做的 / 完成线 / 成本。记做法,不记形状。
- **做法卡要 straight forward,只写被认可的那一种做法**(勾哥 10-16 21:0x"这种在任何情况下都不应该规整,做法卡需要 straight forward")。①卡里不许出现"与参考的差异 / 下次可改成 X"这类没被认可的改法:砖地卡原有一句"下次新环境改成直缝对齐、不转、不掀",丛林地面 spec 引它写了直缝规整,整合照 spec 把荒漠冻结版的不规整开关全关了,返工两轮。②认可做法里的不规整(错行、小转、混型、破边)是做法本身,生成器里写死成冻结值,不留能关掉或调小的 json 字段;卡里只写"换地方只填哪几样"(位置、颜色、相机相关量)。③新 spec 和已有做法卡冲突时以卡为准;写 spec 前先查卡,同类东西有卡就不再对着参考重新复刻一遍。
- 新物件开工前先查做法库,而且要按"卡在原场景里贴着什么"来查,不只看卡名。10-16 23:3x 总控把"沙→草过渡"判成无卡新物件,地面线去生成了正弦边和尖刺叶簇;其实苔藓草皮在荒漠就是铺在沙上的,那圈叶瓣边就是沙草分界。勾哥:"为什么不使用批准的草地?"判"没有卡"之前,把每张卡的认可截图过一遍,问"这张图里有没有这个接缝"。有同类卡:只对新参考重新取卡里列的那几项(一名观察者 + refkit),照卡施工,预期 1-2 轮;没有才走完整 reference-replicate 流程,认可后补卡。
- 生成器代码要按"可复用"写:形状数据(轮廓、叶点)和放置表从外部文件/参数传入,不写死在某个场景里,换环境只换数据。
- 每次复用后在卡的"成本"栏记实际轮次,检验做法库是否真的省时间。
- **全场落地清单,说"已在景"之前先看截图**(10-16 23:2x 勾哥:"感觉你总是不能全局 apply")。总控拿各线自报的标签答"砖→沙就是碎块带,已在场景里",被勾哥一句"你在放屁"驳回:实际只有荒漠搬来的 4 块砂毯,P1、P4 的砖边都是硬切。根因有三:①lead 凭标签答"已落地",没看每一处实例;②冻结卡的"原参数搬"被套到了数量类字段上(砂毯个数),数量应按新场景的边长或面积换算;③交件只看样板那一屏,没有"每屏 × 每种接缝 / 物件"的清单。规则:维护一张全场落地清单(一行 = 一屏的一处实例,写应该用哪张卡、截图上实际是什么、状态),每轮四屏全看完再更新;回答用户"做了没有"之前先查清单和截图。卡的"换地方只填"里,数量类一律写成密度(每米 / 每 H²)。
- **卡冻结当轮就排"铺开"**:scope 里"一类一个样本"只管验证阶段;卡一冻结,lead 要在看板上加一条"按卡铺到所有适用位置"的活,不然场景里只有那一个样本,其余还是占位。10-16 丛林 Lab 草皮/草甸/草芽三卡都冻结了,整屏绿地仍是平涂底板,勾哥问"为什么所有 plan 的绿地不铺上草皮和草呢?given 已经是批准过的做法卡"。离线线(Blender、概念图)冻结的件同理:冻结当轮就排一条引擎线把它导入并摆进场景,lead 维护一张"冻结件 → 是否已在景"清单(按 fbx GUID 查场景引用)。同晚勾哥又问"这些已经批准的不加入 unity 等着干什么呢?",6 件只躺在 staging。
- **搬冻结做法 = 原参数 + 变体全集 + 原铺法,接缝另算新物件**(勾哥 10-16 #42 #44):10-16 丛林整合把荒漠砖地搬过来,只用了 8 种砖型里的完整方砖,又照 Fable 审稿和总控清单把边缘拉直、缺砖改成片,勾哥两次判"不如荒漠""过于规整"。规则:①搬家时卡里列的变体(砖型、叶型、碎块档)全部带上,参数原样;②审稿或卡里"已知与参考不符"那节给出的改法,碰到已冻结的做法一律不进清单,要改先问用户;③两种冻结件在新场景里相接(砖→沙、砖→草、草→崖)是新物件,没有卡,派单第一步写"调 reference-replicate 出观察表交总控",并要求回报附观察表路径——只写"照卡做"执行方不会自己去调(丛林整合线这轮就没调)。
- **组件化**(勾哥 10-16):每一类学习都拆成 3-5 个可单独摆放、可互相搭配的组件(每个 1-3 个变体)+ 参考里实际出现的组合规则(不编),观察表、spec、做法卡都按组件分节,方便大地图 mix & match、逐个组件冻结。

## 3d2 重要节点的产出都过 Fable(勾哥 10-16 18:0x)
"所有比较重要的节点类产出,比如这类,也需要让 Fable 过一下,最大程度减少返工。"重要节点包括:新 spec 派出前、摆位稿、每条新做法线的每一轮最小样、整屏整合。总控出验收清单之前,先开一个 Fable 子 agent 当独立观察者:只给我方截图、参考图、spec 和拍板,不给总控的判断;问"照这个改完还会在哪里不像",最多 6 条,外加最大风险一句话。总控把它的结论和自己的盲看合并后,再发清单。等不到 Fable 结果的,先发总控清单,Fable 的结论进下一轮。
给 Fable 的问法不许圈掉区域("灰盒件不评""只评砖草"):先问整屏"有什么不对",再问具体项。10-16 丛林整合 r1 只让 Fable 评砖草碎块,P1 台顶那块借来的草皮没人看,勾哥看见了。

### 3d3 进 Unity 前的放行闸(勾哥 10-16 20:3x:"为什么这样的东西还能 pass 进入 unity")
10-16 崖壁 r2 把"草掩膜当台地顶"做成一整块绿盖子,离线叠图轮廓、取色 7 点都对上,总控放行进了 Unity;整合 r1 把从别处描来的草皮轮廓贴到台顶中间,总控只看了 P2、P3 两屏。根因:放行看的是代理指标(轮廓重合、取色、指纹),没人先问"参考里从下到上是哪几层、谁盖住谁"。放行前必须:
1. **层序先过**:spec 里写出参考的层序(例:岩壁 → 砂顶 → 砂沿口包岩壁上缘 → 草皮单层伸出崖口),交件图逐层对得上才看轮廓和颜色;层序错了,取色全对也退回。
2. **全屏全量看**:每屏、每件都过一遍(scope 清单逐项点名),不抽样;没看过的屏不许说"过了"。
3. **借来的轮廓/件带着它的上下文**:描图轮廓是贴着某条边描的,换位置必须放到同类边上;没有对应的边就不放,写"缺参考"等补,不"暂借"。执行方自己标了"暂借/没有指定帧"的项,一律当未过处理。
4. **能力测试件不进用户看的视图**:验证生成器入口的测试块(如 blob 示例)放 `WIP/_test` 默认关,不截给用户当候选。
5. **用户原话逐条先核,子线 Fable 不能改写它**(10-17):勾哥看草皮 r1 说"叶瓣边改成参考那种圆钝扇贝、去掉砖区绿点",子线 Fable 审稿建议"其余段近直、叶瓣稀疏成团",r1b 照 Fable 交了撕纸细锯齿边、绿点还在。验收第一步把用户这轮原话拆成条,每条在交件上找到落点(裁局部和参考同比例放大并排),缺一条就退回;Fable 与原话冲突以原话为准,冲突写进退回消息。同日垂柳 #87:更正消息晚于子线提交,交件仍是旧口径(棕枝),收件先核"交件是否含最新一条指令"。
6. **放锁只写在锁文件里,消息里不发"可以取锁"**(10-17 10:3x):总控发给树冠线的"退回修正、锁再点名给你"晚到,那时锁已按放行序交给蕨丛线;树冠线凭消息直接改锁行,在蕨丛 Play 期间改 .cs、重建网格、停了它的 Play。跨会话消息会排队晚到,放行一律只以锁文件"当前持有 / 放行序"为准,消息里只写"按锁文件放行序排队";子线取锁前必须回读锁文件,看到别人持有就停。

## 3e 每次生成先拉参考图(勾哥 10-16)
派单里必须列出这件东西对应的参考图路径和裁区。执行方每轮出图前先打开参考,出图后和参考按同比例并排交件;只交我方单图的,直接退回。代码准备线(先写进暂存目录、还没进引擎的)也一样,要在 README 的验证步骤里写明拿哪几张参考并排。

## 3f 选线:批量和程序化的东西走 Unity 生成器(勾哥 10-16 纠正)
一种东西要铺几十上百个(树、草、碎石),就走 Unity Editor 生成器:json 数据驱动,每档烘 3-4 个变体网格,复用网格走 instancing。理由有三:能在本项目的相机和光下直接调;换 chunk 只换数据;性能可控。管子、壳、叶片这类能用样条或参数生成的有机形(比如巨树的干),也走 Unity。Blender 只留给需要倒角、拼零件、烘图、展 UV 的硬表面单件。10-16 总控先把树冠派给了 Blender,又说巨树干"形状特殊"要留在 Blender,两次都被勾哥问住:都是机械套用了做法库的分工表。

## 4 每张派单附交付检查表,缺项直接退回

- **给用户看的对照图固定三格**:① 参考(文件名)② 现状 = 游戏里当前在景的最好版(commit + 实机截图)③ 修改后 = 本轮(离线/在景 + commit),同比例同 H,每格标题直接写"参考 / 现状 / 修改后"。叠图、指标图另放,不进主对照。10-16 崖壁 r3 交了"参考 / 离线预览 / 50% 叠图",勾哥问"你每次给这个图是什么意思?哪个是现状?哪个是修改后的?"——三格里根本没有现状。lead 转给用户前先查这一条,缺现状格就自己补上或退回。

## 8 巡检看"多久没落盘、在等什么",当场解阻塞

固定 20 分钟巡检常常没东西看,真卡住时又要等下一轮。

## 9 什么时候换掉子会话

先花 5 分钟排除 lead 自己的原因:口径是否在 spec 文件里、稳定、带数字;它读到的是不是最新版;它是否在等正当依赖。这些出问题就先修 lead,换会话没用(10-16 两次差点误杀都是 lead 的锅)。

排除之后,出现下面任一条就换:

1. 自报的数字、状态、"已完成"被独立手段核实为假,两次即换。这是最强信号。
2. spec 稳定且给了数,同一缺陷两轮不收敛,或在两头来回摆。
3. 交付比当前最好版差,却没指出也没回退。
4. 明确指令后仍绕回老做法,提醒一次后再犯。
5. 20-30 分钟无落盘且说不出在等什么,或同一失败命令连跑 3 次以上。
6. 越界:改 scope 外的文件、push、删资产、违反红线。立刻停。

另有一种不算能力问题:上下文过长(上千条消息),症状是忘早先的规矩、混淆版本、重复问已定的事。到里程碑就主动轮换,不等犯错。

换的流程:stop_session(旧会话留着不删,归档要用户点头)→ 让它或 lead 写交接(`templates/handoff.md`:当前最好版 commit、spec 文件与版本、产出路径、已排除做法、踩过的坑)→ 新会话只从文件接手。
