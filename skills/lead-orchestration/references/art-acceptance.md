# 美术线派单与验收细则(从 lead-orchestration 主干挪出)

带美术线(建模、地编、植被、出图、对标参考复刻)时读这份。节号保留原 skill 的编号，方便和旧交接对上。调度、派单、巡查、换人、并排验收的通用规矩以主干 SKILL.md 为准；两边冲突以主干为准。看图验收方法另见 reference-replicate。

### 2b spec 发出前的检查

- 每一条要求必须填"对应参考的哪一段"(文件 + 坐标)。填不出的不许发。
- **禁止"加/补某个形状"的要求,除非能指出参考里对应的那一段。** 没有参考段的"沿边加叶瓣""零星探出"会让执行方回到参数生成,做出圆泡和水滴,比上一版还差。
- 每条视觉要求都要加一列"机制":写清在本项目着色器下这个效果靠什么出来,是光照、顶点色、ramp、贴花,还是烘焙 mask。spec 只写"要渐变 / 要三档明暗 / 要软影"而当前着色器做不出来时,第一轮注定是一刀切的硬边。
- 颜色要写明是"屏幕色"还是"材质色"。屏幕色要闭环标定:在本项目的光下截图取色,反推材质色;把屏幕色直接填进材质,太阳一照会偏亮偏黄。
- 观察者"推断"出来的项(没有直接样本)不进要求,写进待核。
- 主体件、地面、整屏的 spec 发给执行方前,必须过 3d2 的独立审稿关口:只给裁好的同比例参考图 + 合并观察表 + spec,问"照这个做第一轮会在哪里不像",≤5 条(独立审稿常能拦下总控和双观察者都漏掉的错)。

### 2c 第一轮只交摆位稿

新物件第一轮不做形状和材质细节,只交"摆位稿":纯色占位块在本项目相机下摆好位置、朝向、大小、贴着哪条边界,和参考同比例叠图对照。lead 确认后才进形状和材质。真正影响"像不像"的常是整块转了 90°、孤立摆在空地中间这类摆位错,细节调得再好也救不回来,所以摆位第一步定。

- 摆位要求必须给出参考里对应那一块的两端、宽窄变化和它贴着/压着什么,不能只写方向(只写"长轴沿崖沿"会被做成横贯全屏的带子)。
- 摆位要求里的尺寸先在本项目相机画面里量一遍容量再写,写出画面装不下的尺寸会让执行方停下来问;小取舍授权执行方自定,只给不可违反的几条底线。
- 摆位稿只做纯色占位,完整生成器等摆位确认后再写。体量较大的新资产(草甸、崖壁)在摆位稿之后再做一小块测试块,过了才铺开。
- 验收多屏摆位稿时,先拿 scope 清单逐项点名:每一项在哪一屏、单看灰盒能不能认出是它。几项被合成一个东西的(比如"地面上的台地"和"世界边缘"做成一列台阶),要拆开。

## 3 验收一次给全,执行方回合中不追加零碎

一次给全、回合中不追加、急事先 stop 再发合并清单、一回合一段,以主干第 4、7 节为准。美术线另加两条:

- 每次验收按 reference-replicate 第 4 节,从头到尾全部量完,一张清单一次发出(同时更新 spec 版本)。
- 修改单里的"必须保留"项只写文字不够,执行方照样会丢:保留项要变成交件的一格验收图(和修前同机位并排,标出那几项),执行方交件前自己对一遍。

## 3b 什么时候算 OK、什么时候停

"找不出三处差异才算过"没有终点,差异永远找得到;拿放大图和够不着的指标去追,会一轮比一轮加工得多、越改越坏(零加工的描图版往往最好)。所以:

1. **开工前定"完成线"**:每类物件只列 3-5 条在实机尺度(本项目相机全屏、手机实际大小)看得出的关键项,写进 spec。验收只看这几条,不在放大图上找新问题。
2. **差异分两类**:实机全屏看得出的才开新一轮;放大才看得出的(像素阶梯、细尺度起伏、几个 px 的色差)只记录,不开轮。
3. **够不着的指标直接放弃**:受参考分辨率限制达不到的数,不追,写进"已知限制"。
4. 每轮必须赢过当前最好版(没赢就回退并停下,除非有新的参考信息)、同一物件最多 3 轮(到上限把最好版和"建议冻结"给用户看)、用户说可以就当轮冻结(剩下的差异记进待办),以主干第 7 节为准。

## 3c 第二轮起让用户判,并从他的判断里学标准(勾哥定)

- 每个物件做完第一、二轮后,从第二轮起每轮把"当前最好版 vs 本轮"实机全屏并排,用弹窗让用户判:冻结 / 再改一轮(写清改什么)/ 方向不对。lead 先把自己的判断写下来,再看用户选。
- 维护一份"用户判断标准库"(共享笔记,如 15_勾哥判断标准库.md):每条记时间、看的是什么、原话、lead 当时的判断、差在哪、推出的标准。原话照记,不升级不降级。
- 每次验收前先读标准库;lead 和用户判断不一致时以用户为准,把推出的标准写回标准库,能泛化的再写进 reference-replicate 或本 skill。
- 目标是 lead 的判断逐步和用户对齐,用户需要介入的次数逐轮减少;每周期看一次"lead 判断与用户一致的比例"。

## 3d 认可即入做法库,新物件先查做法库(勾哥定)

- 用户认可/冻结一套做法的当轮,lead 写一张做法卡进项目的做法库(ER:vault `013 美术/复刻做法库/`):认可原话 / 一句话做法 / 步骤与工具(脚本、命令、参数)/ 换环境时要重新取的 / 不要做的 / 完成线 / 成本。记做法,不记形状。
- **做法卡要 straight forward,只写被认可的那一种做法**(勾哥原话"做法卡需要 straight forward")。①卡里不许出现"与参考的差异 / 下次可改成 X"这类没被认可的改法:后来的 spec 会引它,把冻结版的做法改掉,返工。②认可做法里的不规整(错行、小转、混型、破边)是做法本身,生成器里写死成冻结值,不留能关掉或调小的 json 字段;卡里只写"换地方只填哪几样"(位置、颜色、相机相关量)。③新 spec 和已有做法卡冲突时以卡为准;写 spec 前先查卡,同类东西有卡就不再对着参考重新复刻一遍。
- 新物件开工前先查做法库(项目里有已验收的成套套件时,套件优先于卡;卡里写的和勾哥最新反馈冲突时以最新反馈为准),而且要按"卡在原场景里贴着什么"来查,不只看卡名:一个看似新的接缝(如沙→草过渡)可能就是某张卡原场景里本来就有的边。判"没有卡"之前,把每张卡的认可截图过一遍,问"这张图里有没有这个接缝"。有同类卡:只对新参考重新取卡里列的那几项(一名观察者 + refkit),照卡施工,预期 1-2 轮;没有才走完整 reference-replicate 流程,认可后补卡。
- 生成器代码要按"可复用"写:形状数据(轮廓、叶点)和放置表从外部文件/参数传入,不写死在某个场景里,换环境只换数据。
- 每次复用后在卡的"成本"栏记实际轮次,检验做法库是否真的省时间。
- **全场落地清单,说"已在景"之前先看截图**(勾哥:"感觉你总是不能全局 apply";凭各线自报答"已在场景里",实际常只有样板那一屏落了)。规则:维护一张全场落地清单(一行 = 一屏的一处实例,写应该用哪张卡、截图上实际是什么、状态),每轮所有屏全看完再更新;回答用户"做了没有"之前先查清单和截图。卡的"换地方只填"里,数量类一律写成密度(每米 / 每 H²),不照原场景个数搬。
- **卡冻结当轮就排"铺开"**:scope 里"一类一个样本"只管验证阶段;卡一冻结,lead 要在看板上加一条"按卡铺到所有适用位置"的活,不然场景里只有那一个样本,其余还是占位。离线线(Blender、概念图)冻结的件同理:冻结当轮就排一条引擎线把它导入并摆进场景,lead 维护一张"冻结件 → 是否已在景"清单(按 fbx GUID 查场景引用;勾哥:"这些已经批准的不加入 unity 等着干什么呢?")。
- **搬冻结做法 = 原参数 + 变体全集 + 原铺法,接缝另算新物件**(只搬一种变体、把不规整的边拉直,会被判"过于规整"):①搬家时卡里列的变体(砖型、叶型、碎块档)全部带上,参数原样;②审稿或卡里"已知与参考不符"那节给出的改法,碰到已冻结的做法一律不进清单,要改先问用户;③两种冻结件在新场景里相接(砖→沙、砖→草、草→崖)是新物件,没有卡,派单第一步写"调 reference-replicate 出观察表交总控",并要求回报附观察表路径——只写"照卡做"执行方不会自己去调。
- **组件化**(勾哥定):每一类学习都拆成 3-5 个可单独摆放、可互相搭配的组件(每个 1-3 个变体)+ 参考里实际出现的组合规则(不编),观察表、spec、做法卡都按组件分节,方便大地图 mix & match、逐个组件冻结。

## 3d2 重要节点的产出都过独立审稿(勾哥定)

勾哥原话:"所有比较重要的节点类产出……也需要让 Fable 过一下,最大程度减少返工。"做法:开一个干净上下文的独立审稿 agent,用哪个模型勾哥当次说。重要节点包括:新 spec 派出前、摆位稿、每条新做法线的每一轮最小样、整屏整合。总控出验收清单之前,先开一个独立审稿子 agent 当独立观察者:只给我方截图、参考图、spec 和拍板,不给总控的判断;问"照这个改完还会在哪里不像",最多 6 条,外加最大风险一句话。总控把它的结论和自己的盲看合并后,再发清单。等不到审稿结果的,先发总控清单,审稿结论进下一轮。

给审稿方的问法不许圈掉区域("灰盒件不评""只评砖草"):先问整屏"有什么不对",再问具体项。圈掉的区域没人看,最后由勾哥看出来。

### 3d3 进 Unity 前的放行闸(勾哥:"为什么这样的东西还能 pass 进入 unity")

放行只看代理指标(轮廓重合、取色、指纹)会放过结构错:例如把"草掩膜"当成台地顶做成一整块绿盖子,轮廓和取色全对上。根因是没人先问"参考里从下到上是哪几层、谁盖住谁"。放行前必须:

1. **层序先过**:spec 里写出参考的层序(例:岩壁 → 砂顶 → 砂沿口包岩壁上缘 → 草皮单层伸出崖口),交件图逐层对得上才看轮廓和颜色;层序错了,取色全对也退回。
2. **全屏全量看**:每屏、每件都过一遍(scope 清单逐项点名),不抽样;没看过的屏不许说"过了"。
3. **借来的轮廓/件带着它的上下文**:描图轮廓是贴着某条边描的,换位置必须放到同类边上;没有对应的边就不放,写"缺参考"等补,不"暂借"。执行方自己标了"暂借/没有指定帧"的项,一律当未过处理。
4. **能力测试件不进用户看的视图**:验证生成器入口的测试块(如 blob 示例)放 `WIP/_test` 默认关,不截给用户当候选。
5. **用户原话逐条先核,子线审稿不能改写它**:验收第一步把用户这轮原话拆成条,每条在交件上找到落点(裁局部和参考同比例放大并排),缺一条就退回;审稿与原话冲突以原话为准,冲突写进退回消息。更正消息可能晚于子线提交到达,收件先核"交件是否含最新一条指令"。
6. **放行只以锁为准,消息里不发"可以取锁"**:跨会话消息会排队晚到,凭晚到的消息改锁会停掉别人的 Play。子线取锁前必须回读锁(现行 `Tools/cargo_lock.sh`),看到别人持有就停。
7. **用户说"我一个一个盯"时,进引擎的放行权归用户**(勾哥:"我什么时候让你上的?"):lead 并排看过只算预审,离线稿摆给用户问,用户点头才放这条线进引擎。

## 3e 每次生成先拉参考图(勾哥定)

派单里必须列出这件东西对应的参考图路径和裁区。执行方每轮出图前先打开参考,出图后和参考按同比例并排交件;只交我方单图的,直接退回。代码准备线(先写进暂存目录、还没进引擎的)也一样,要在 README 的验证步骤里写明拿哪几张参考并排。

**参考登记表**(根治子会话乱用参考):一物一行锁定参考,登记表位置和取用规矩见 reference-replicate 第 0 节,要加先报 lead 写理由。交件图里每个参考格的标题写登记的路径和裁区,lead 转给用户前逐格对表,对不上就退回。别的线的交付目录只借工具和脚本,不借图。

概念图喂哪些参考、用哪套出图配方、颜色从哪取,按 vault `013 美术/AI记忆/现行口径_生图与概念图.md` 第二、四、五节。

## 3f 选线:批量和程序化的东西默认走 Unity 生成器(勾哥纠正)

一种东西要铺几十上百个(地形上的树、草、碎石),默认走 Unity Editor 生成器:json 数据驱动,每档烘 3-4 个变体网格,复用网格走 instancing。理由有三:能在本项目的相机和光下直接调;换 chunk 只换数据;性能可控。单项件怎么分工,以 vault `013 美术/AI记忆/现行口径_参考与工具分工.md` 第一节工具分工表为准。别的路线可以试,按实拍和参考并排判。派线前对着活本身想一遍,不机械套分工表。

## 4 每张派单附交付检查表,缺项直接退回

执行方只检查派单让它检查的东西:面积误差、法线这些都达标,"像不像参考"不在它的检查项里,外观问题全流到用户眼前。

- 派单附 `templates/deliverable_checklist.md`(含「美术线另加」一段),缺任何一项 lead 不看图直接退回。派 `executor` / sol 的写法见主干第 4 节。
- **给用户看的对照图固定三格**:① 参考(文件名)② 现状 = 游戏里当前在景的最好版(commit + 实机截图)③ 修改后 = 本轮(离线/在景 + commit),同比例同 H,每格标题直接写"参考 / 现状 / 修改后"。叠图、指标图另放,不进主对照。缺现状格勾哥看不出改了什么;lead 转给用户前先查这一条,缺就自己补上或退回。
- **退步拦截**:执行方交付前必须和当前最好版对比(`refkit.py regress` 或 shape 指标 + 并排图),任一项变差就不交、先回退;lead 第一眼判好坏见主干第 7 节。

## 5 半成品不进用户看的视图

未标定的半成品(比如过曝的颜色)被勾哥直接看到,等于替他做了错误的初判。

- 执行方的新内容默认放在一个关着的 WIP 节点下(或场景副本),lead 验收通过才打开、并入用户看的那份。
